# 留出集评测报告：语料覆盖度对召回的敏感度

> 实测日期：2026-09-15 ｜ 语料 v1.13.0（73 意图 / 554 问法）｜ 测试集 207 条（可答 204 / 应拒答 3）
> 复现：`python scripts/evaluate_holdout.py --ks 8,6,5,4,3 --seeds 3`

---

## 0. 一句话结论

**语料的问法覆盖面是这套系统最主要的杠杆**：每意图从 8 条砍到 3 条，
召回@1 从 **96.7% 掉到 76.5%**（−20.2 个百分点），而且**下降几乎是线性的、看不到饱和点**。

这**证实了 README 里那条此前从未被验证过的核心论断**——
「把每条问法补到 8 条覆盖不同说法，收益大于换更强的算法」。

⚠️ 但要读准它证实的**是**什么：它说明**索引覆盖度决定召回上限**，
**不**说明"继续往现有测试集上堆问法还能涨"（现有测试集已 99%，被自己的问法分布封顶了）。见 §5。

---

## 1. 为什么要做这个

两个动机，第二个才是关键：

1. **README 的核心论断从没被验证过。** 「补问法 > 换算法」是项目对外的主论点之一
   （见 README「为什么不用更强的模型」一节），但一直只是**论断**——没有任何实验支撑它。
2. **"开放集评测"做不了，需要找一个诚实的替代。** 原计划用线上未命中日志
   `logs/unmatched.jsonl` 当开放集，核实后发现**不行**：
   5849 行里去重仅 210 条，高频项全是压测脚本循环打的（`图书馆几点开门` 554 次…），
   且 **210 条里有 132 条直接来自 `tests/test_set.json`** —— 拿它当开放集是**循环论证**。
   项目**没有真实用户数据**。

留出集是能立刻做、且结论可辩护的替代方案。

---

## 2. 方法

```
对每个 K：每个意图**随机保留 K 条**问法建索引，其余留出（固定种子，跑 3 个随机划分取均值）

探针 A（主）：tests/test_set.json 207 条
              —— 它不在语料里（有断言保证），是"真正没见过的说法"
探针 B（辅）：被留出的语料问法（K=3 时 335 条）
              —— 测"自己的问法能否被兄弟问法召回"

基线：全量 554 条问法建索引，跑同一个探针 A
```

语料实况：每意图问法数 **最少 4 / 中位 8 / 最多 16**（所以 K=3 是能压到的最低档之一）。

**口径说明**：本表的召回@1 把「未识别」（余弦 < `SIMILARITY_THRESHOLD` 0.60）**也算作未命中**，
比 `evaluate.py` 更严格 —— 所以基线在这里是 **99.0%** 而不是 README 里的 **99.5%**（差 1 条）。
两个数都对，只是口径不同。

---

## 3. 结果

| 索引 | 问法数 | **召回@1** | Top-3 | 未识别 | 误触发 |
|---|---|---|---|---|---|
| **全量（基线）** | 554 | **99.0%** | 100.0% | 0.0% | 0/3 |
| 每意图留 8 条 | 520 | 96.7% | 98.2% | 1.0% | 0/3 |
| 每意图留 6 条 | 427 | 91.8% | 95.3% | 1.8% | 0/3 |
| 每意图留 5 条 | 363 | 88.1% | 92.8% | 4.2% | 0/3 |
| 每意图留 4 条 | 292 | 82.4% | 88.1% | 6.5% | 0/3 |
| 每意图留 3 条 | 219 | **76.5%** | 83.7% | 10.1% | 0/3 |

（3 次随机划分的极差：K=3 时 75.0%~77.5%，K=8 时 96.1%~98.0% —— 抽样噪声约 ±1.5pt，趋势远大于噪声。）

### 逐档下降幅度

| 变化 | 召回@1 变化 |
|---|---|
| 554 → 520（只少 34 条，−6%） | **−2.3pt** |
| 520 → 427 | −4.9pt |
| 427 → 363 | −3.7pt |
| 363 → 292 | −5.7pt |
| 292 → 219 | −5.9pt |

**两个值得注意的点**：

1. **第一档就掉 2.3pt**：只删了 34 条问法（索引缩小 6%），召回就掉了 2.3 个百分点。
   说明**在顶部也很陡**——不是"删到某个临界点才崩"，而是删哪条都会伤到那一类说法。
2. **没有饱和/递减趋势**：每档掉 4~6pt，几乎线性。
   如果"堆问法"是边际收益递减的，曲线应该越往上越平；实测**不平**。
   反过来说：**这套语料远没到"问法够多了"的程度。**

## 4. 探针 B：我预判错了

我原本在脚本注释里预判"自己问法找兄弟问法自然更容易"，实测**反了**：

| 探针（K=3 时） | 召回@1 | Top-3 | 未识别 |
|---|---|---|---|
| A：测试集问法 | 76.5% | 83.7% | 10.1% |
| **B：留出的语料问法** | **68.7%** | 77.6% | 10.7% |

**为什么语料问法反而更难**：语料里存在大量**短句 / 省略式**问法（"多少钱""怎么申请""在哪看"），
单条自身区分度低，得靠"同意图的其他问法一起把话题托住"。
一旦索引里只剩 3 条，"托住"的力度就不够了。

这与 `docs/rerank_report.md` 里那条发现是**同一件事的两面**：
精排失败的成因是「**句式压过话题**」，这里失败的原因是「**话题词太弱、句式太通用**」。
两条独立实验指向同一个结构性事实：**这套语料的问句普遍短且句式雷同，区分度主要靠话题词，而话题词往往只出现在少数问法里。**

---

## 5. 这个结论能说什么、不能说什么

**能说**：

- 索引覆盖度是召回的主要杠杆；缩容会立刻、且近似线性地伤召回。
- 因此 README 的论断（补问法 > 换算法）方向正确，**现在有数据支撑了**。
- 每意图只留 3 条时未识别率升到 10.1%（用户会看到"这题我答不上"），
  这是**产品可用性**层面的直接证据：问法太少的意图对用户表现为"答不上"而不是"答错"。

**不能说**：

- ❌ **不能说"继续扩语料能把 99% 提到更高"**。现有测试集只有 207 条、且由同一作者撰写，
  索引已经能覆盖它的问法分布 —— 它被自己的分布**封顶**了。继续扩语料的真实收益在
  **尚未被想到的长尾问法**上，而那部分**现有测试集测不到**。
- ❌ **不能把这个当"开放集"**。语料与测试集出自同一作者、用词习惯一致，
  绝对数字偏乐观；本报告只声称**相对趋势**有信息量。
- ❌ 不能推断线上表现。项目**没有真实用户数据**（见 §1）。

## 6. 可操作产出：优先补哪些意图的问法

索引最稀疏时（每意图留 3 条）**掉得最多**的意图 —— 它们的问法覆盖最薄：

| 意图 | 错误率 | 测试集里几条 |
|---|---|---|
| `xsc_commute_apply`（走读申请） | 100% | 2 |
| `enrollment_report`（新生报到） | 100% | 3 |
| `xsc_dorm_6s`（公寓 6S 管理） | 80% | 5 |
| `xxh_wifi_drop`（校园网掉线） | 67% | 3 |
| `lost_found`（失物招领） | 67% | 3 |
| `canteen_info`（食堂餐饮） | 67% | 3 |

⚠️ **分母很小（2~5 条）**，单条就能让百分比跳 20~50 个点，**只能当线索、不能当定论**。
要确认得给这些意图补测试样本，或者逐个意图看它的问法是不是都很短、都很像。

注意 `enrollment_report` 在这里错误率 100%，而它在全量索引下只错 1 条
（就是那条歧义测试句「去学校要准备什么证件和材料」，见 README 已知限制）——
**这恰恰说明它属于"问法覆盖薄"的类型**：索引一缩就顶不住。

## 7. 复现

```bash
python scripts/evaluate_holdout.py --ks 8,6,5,4,3 --seeds 3
```

约 1.5 分钟（BGE 只加载一次，各档复用同一个 vectorizer——BGE 不训练，`fit` 只是加载模型）。
脚本**不经过安全层**（直接调 `retriever.search`），理由同 `benchmark_rerank.py`：
批量走 `ask()` 会全落进同一个 IP 限流桶，召回率会假跌。
